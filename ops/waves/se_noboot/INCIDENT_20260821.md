# INCIDENT — NOBOOT wave ran the bootstrapped arm (21 Aug 2026)

## What happened

All four `se_noboot_s40..43` runs completed (5/5 milestones, ~6.3 h
each) with `disag_bootstrap: true` — the bootstrapped Stage-1 arm
wearing noboot run_ids. `DISAG_BOOTSTRAP=False` was silently inert.
~25 GPU-h produced the wrong arm. No outcome values were read (ops
verified config identity + progress counters only); the frozen
`se_noboot_read` config pin would have refused the runs — the
backstop worked as designed.

## Root cause (diagnosed 21 Aug, paper-5 chat)

**Stale producer checkout on the instances.** Eliminations:
- The wave spec and every generated lane cmd carry
  `DISAG_BOOTSTRAP=False` inline (verified in
  `generated/lane_train_*.cmds` and `runs.json`).
- The parse path is correct: reproducing main.py's exact config
  composition locally with the producer's argv yields
  `disag_bootstrap = False`.
- `RUN_ID/TASK/SEED` from the SAME prefix-assignment list all bound
  (dirs and seeds are right), so the env mechanism worked.

What remains — and fits every observation: the
`--agent.expl.disag_bootstrap "${DISAG_BOOTSTRAP:-True}"` line was
added to `scripts/uncfield_se.sbatch` **in the NOBOOT freeze commit
818a3f7a itself**. The lane cmds do not git-pull (they `cd "$REPO"`
and run), and `preflight_remote.sh` checks file EXISTENCE, python,
rsync/tar, disk — never repo SHA or file content. An instance whose
fork was pushed before 818a3f7a ran the amendment-3-era producer, in
which `DISAG_BOOTSTRAP` is an UNREAD variable — the exact hazard the
spec's own NOTE documented ("an unread env var is not an error").

## Fixes

1. **Producer BIND-CHECK (implemented 21 Aug, this repo):**
   `scripts/uncfield_se.sbatch` now waits for `config.yaml` after
   launch and asserts every wave-critical override bound
   (disag_bootstrap, dim, scale, mod_key, both gate_keys, expl.mode),
   killing the run within minutes on any mismatch or missing key.
   Validated against the flat/hetero grad-wave configs (passes on
   matching env, fails on mismatch and on missing keys). This guard
   cannot protect a checkout that predates it — hence fix 2.
2. **Wave preflight (ops chat to implement in wavegen):**
   (a) stamp the generator's HEAD SHA into the generated preflight
   and assert `git -C $REPO rev-parse HEAD` matches (or is a
   descendant) on the instance; (b) for every `VAR=` token in a lane
   cmd, `grep -q '${VAR'` in the script the cmd invokes — the
   mechanical "every env var this wave sets is actually read" check.
   **URGENT: A1/B1/B2 ride the same route and depend on
   DISTRACTOR_MOD_* / DISTRACTOR_SCALE / EXPL_CONFIG.**

## Disposition of the four spoiled runs

- ARCHIVE-FIRST, then rename on RCC to
  `se_noboot_s4X_SPOILED_BOOTON` (never delete; standing rule). The
  rename keeps any future `se_noboot_s*` glob from touching them;
  the reader's config pin remains the second lock.
- They are clean bootstrapped Stage-1-config runs at fresh seeds
  40–43 — parked as a potential DESCRIPTIVE replication set; not
  registered for anything.
- No prereg amendment needed: the registered arm never ran and no
  outcome was observed, so re-running seeds 40–43 as registered is
  clean. This note + the ledger row + a provenance line in the
  eventual read RECORD are the registration-hygiene trail.

## Re-run protocol

1. Push current HEAD to the target instances (the bind-check and the
   flag both ride in it); run the upgraded preflight.
2. Resubmit the SAME generated lane cmds (they were always correct),
   seeds 40–43, registered run_ids.
3. Watch the first minutes: each run must print
   `BIND-CHECK PASS: all wave-critical overrides bound` and its
   `config.yaml` must show `disag_bootstrap: false` (the wave
   checker's `done_when` pin also enforces this at completion).
